# Custom Detector Priority and Distance Alert Policy — Implementation Plan

**Task type:** logic/alert-policy change; no intentional visual changes.

**Required input:** [`custom-detector-priority-distance-alert-policy-analysis.md`](custom-detector-priority-distance-alert-policy-analysis.md).

## Goal and scope

Implement a custom-detector-only automatic safety-alert policy that combines the detector's verified identity/label priority with eligible fresh metric distance, while preserving built-in COCO behavior, existing label mapping, unknown-label fallback, scheduler lifecycle, and user-initiated Quick Scan behavior.

The phrase “custom detector” means an imported detector model currently executed through the Ultralytics path. It does **not** mean restoring the removed Custom EyeCue inference engine. No visual changes, model-import contract changes, depth model changes, speech-platform changes, or broad architecture edits are in scope.

The policy boundary is automatic alerts: the controller's existing normalized detections and `DetectionInfo`, plus detector-model context, feed the shared `AlertPolicy`; the existing TTS scheduler remains the sole serialized speech executor. Do not alter built-in alert ranking/risk or the scene-wide Quick Scan ranking/wording. Where the request's named behaviors imply semantics not fixed by the verified code, this plan labels the proposed behavior Needs Verification instead of treating it as settled product policy.

## Source-of-truth and non-regression constraints

1. Use verified active detector identity (`DetectorModelKind` plus the selected model's immutable identity/fingerprint) as the scope switch. Never infer “custom” from class index, label text, engine enum, or the string `custom` alone.
2. For the built-in model, preserve asset label index mapping and existing COCO `classId` priority. Preserve the selected detector's own label sequence for custom models; a valid class index maps through that active sequence, while an invalid index or unavailable/empty resolved label retains the adapter's current native-result label fallback. An unknown but non-empty custom label remains unknown to the custom semantic classifier and uses its explicit safe fallback; it must not accidentally inherit COCO priority from its numeric class ID.
3. Preserve the currently verified narrow custom label sets and normalization unless the user approves an explicit mapping replacement. The analysis establishes that those sets already exist; there is no verified new set of custom priority classes in the task description. The proposed combined policy uses the existing resolved `ObjectPriority` as its priority input.
4. Metric distance is eligible for policy only when the detector-index-aligned sample is present, finite, within `DepthDistanceService`'s valid metric bounds, and supplied from the currently fresh, geometry-matched depth frame. Preserve the existing `depthStaleAfterMs` freshness gate and active-frame sampling path. Missing, stale, malformed, out-of-range, or misaligned metric data is not “metric near”; it follows the existing bounding-box heuristic path and remains distinguishable as heuristic/approximate in `DetectionInfo`.
5. Do not describe model-produced metres as calibrated ground truth. Metric thresholds already verified in code map `<=1.5m` to near and `<=4m` to medium; policy-specific thresholds beyond those values are not confirmed and must remain configurable/proposed pending product and device verification.
6. Do not change history at decision time. Preserve `AlertPolicy.decide` as read-only, commit suppression/escalation history only after confirmed speech start, and preserve pending-request revalidation immediately before speech start.
7. Candidate choice must retain the existing invariant that a suppressed primary cannot be replaced by a lower-ranked candidate unless that candidate independently qualifies as a new identity or escalation. Existing track-first/label-fallback identity remains unchanged.

## Behavior conflicts and proposed resolution

| Conflict | Verified existing behavior | Plan resolution |
|---|---|---|
| Priority versus distance precedence | Shared ranking is priority → motion → proximity → confidence → label/class ID; changing it globally affects built-in and custom models. | Keep the shared ranker and built-in ordering unchanged. Add custom-aware alert eligibility/risk evaluation at the `AlertPolicy` boundary using the candidate's `DetectionInfo` and verified detector scope. Whether custom metric distance should outrank a higher object-priority candidate is **Needs Verification**; proposed default is not to reorder shared candidates, but permit eligible custom distance to affect that candidate's own risk/escalation. |
| Metric versus box-size heuristic | Both currently produce a proximity band; `DistanceSource` distinguishes the source and approximate fallback. | Only fresh valid metric values may trigger the new metric-based safety eligibility/escalation. Heuristic proximity continues current alert behavior, is explicitly treated as approximate, and must not be represented as a confirmed metric-distance threshold crossing. Exact interactions with existing heuristic-based urgency are **Needs Verification**. |
| Center corridor relevance | Center position currently contributes to high risk and center-entry escalation; it can make heuristic-only candidates urgent. | Preserve the built-in behavior. For custom policy, retain center as a relevance qualifier for a custom hazard candidate, but do not allow center alone to impersonate a metric threshold crossing. Proposed relevance rule: metric-based distance alert/escalation requires a center-path candidate; outside-center candidates continue to be governed by existing ordinary/custom priority and motion behavior. Whether “center path” should suppress all side detections or only distance-triggered alerts is **Needs Verification**. |
| Hysteresis and repeat behavior | Existing escalation has a minimum gap, risk transition, approach transition, center entry, and height growth; the scheduler has cooldown, deduplication, and pending validity/revalidation. | Implement distance-threshold hysteresis as state associated with the existing alert identity, without adding a competing scheduler or committing on decision. Require a confirmed metric transition across the configured alert threshold to escalate; require crossing a distinct lower reset threshold to re-arm. Thresholds, consecutive-sample count/debounce, state expiry, and whether loss of metric resets or preserves hysteresis are **Needs Verification**. Proposed initial behavior: preserve last metric state through one invalid/stale frame, do not escalate from it, and clear/re-arm only under an explicit reset/identity-expiry policy—not from the heuristic estimate. |
| Detector identity and model switch | The selected model has kind, fingerprint, labels and a compact ref; current model can change at runtime. | Bind policy state/decisions to the active detector identity as well as existing track/label key, so a new model cannot inherit another model's distance escalation history. Clear or namespace policy state when model identity changes. Exact lifecycle of queued speech across model switch is **Needs Verification**; pending alert must be revalidated against current detector identity before it starts. |
| Spoken alert wording | Existing normal and urgent wording consumes current label, priority, position, proximity/distance and motion. | Keep current phrases unless approved wording is provided. Any metric-specific wording must retain the existing cautious “about” estimate semantics; do not claim calibrated distance. Wording changes are **Needs Verification**. |

## Stepwise implementation

1. **Lock policy identity and label resolution.** At active model selection, distinguish `builtIn` from imported `custom` using `DetectorModelKind` and stable active model identity. Verify the resolved class label comes from the selected model's own ordered labels when class index is valid. Preserve native result class name fallback for invalid/unavailable mapping and classify unmatched custom labels using the existing explicit unknown/low fallback. Ensure no custom class ID is looked up in the COCO table. Keep built-in asset order, label mapping, and class-ID priority byte-for-byte behaviorally equivalent.
2. **Define one custom policy input.** Represent the candidate's resolved object priority and distance evidence as a single custom alert-policy input, sourced from `DetectionInfo` plus active model identity. Keep distance source explicit: fresh metric, heuristic bounding-box, or unavailable/invalid. Do not infer metric evidence from `ProximityBand` alone because both metric and heuristic paths populate that band. Preserve existing spatial analysis and UI-facing values unless a verified policy requirement demands otherwise.
3. **Enforce fresh metric-only eligibility.** At the screen/controller boundary, pass a metric eligibility signal only from the current fresh and geometry-matched depth frame, aligned to the correct detection, finite, and within valid limits. Invalid/stale/missing samples must not create a metric trigger. Keep the existing heuristic proximity and warning distinction; it may continue ordinary existing policy behavior, but must not be described as crossing a metric threshold. Do not let one detection's sample shift to another after missing index entries.
4. **Resolve candidate selection without broad ranking changes.** Continue to use `SceneSummaryService.rankCandidates` as the sole deterministic ranker. Add the custom-only combined priority-distance qualification in `AlertPolicy` around candidate qualification/risk/escalation; do not sort a second time or alter built-in risk. A candidate with eligible fresh metric distance may gain custom alert risk under the approved thresholds, combined with the existing custom `ObjectPriority`; exact combination/precedence remains a proposed product decision. Preserve the rule that a suppressed primary cannot cause an unqualified substitute to be spoken.
5. **Apply center-path relevance.** For the proposed custom metric trigger, require the candidate to satisfy the approved center-path condition; center alone does not prove metric proximity. Preserve existing center-entry logic for built-in alerts. Do not globally remove center as a risk factor because that changes established built-in behavior. Tests must cover centered and side-position cases, including custom high priority and metric-near cases, after the rule is approved.
6. **Add distance hysteresis and escalation safely.** Extend existing per-identity policy history with the minimum state needed to avoid repeated threshold chatter. Trigger only on an eligible threshold transition and enforce the existing escalation gap/cooldowns. Reset/re-arm only on the approved lower hysteresis boundary or explicit identity/state expiry. Decisions remain pure; record the transition only through confirmed `commitStarted`. Integrate distance transition with existing risk/proximity/approach/center/height escalation without weakening those safeguards. Exact thresholds, debounce, reset semantics, and whether metric distance alone can escalate a low-priority custom label remain **Needs Verification**.
7. **Preserve TTS pending arbitration and deduplication.** Use existing `AlertDecision`, `TtsService` serialized one-active/one-pending queue, scheduler cooldown/preemption, and `shouldSpeakPending` revalidation. Include detector identity and distance eligibility in pending revalidation such that stale, invalidated, or model-switched decisions cannot speak based on old metric evidence. Do not mutate alert state on queued/submitted/cancelled/completed signals; only confirmed start commits. Preserve urgent/imminent preemption semantics unless explicitly approved otherwise.
8. **Keep Quick Scan separate.** Do not route `quickScan` through custom safety-alert policy, custom threshold eligibility, or alert suppression/hysteresis history. Preserve whole-scene summary, spatial grouping, user-initiated priority, and current summary ranking. Only change it if a separate explicit requirement is approved.
9. **Update policy documentation.** Document approved custom policy, source distinction between metric and box-size estimate, known uncalibrated depth limitation, fallback behavior, and verified initial tuning defaults/device-validation status. Do not publish proposed values as settled defaults. Update implementation decisions only for a confirmed change to an existing decision; update testing plan only for confirmed new verification requirements.

## Test plan — requested coverage

Add targeted deterministic unit/regression tests only in the justified test files above. Preserve existing coverage and inspect existing tests before changing them.

1. **Identity and label verification:** bundled COCO label/index mapping and priority remain unchanged; custom active label list maps valid indices; invalid/unavailable mapping keeps native class name fallback; unknown custom label remains safe low/unknown and never inherits COCO class-ID priority; normalization does not cross model identity.
2. **Combined policy and selection:** custom priority plus approved metric evidence produces the expected eligible candidate/risk; metric-versus-priority tie/precedence cases are covered; built-in behavior is regression-tested unchanged; a suppressed primary does not promote an unqualified lower candidate; the authoritative ranker remains the only sort.
3. **Metric freshness/validity:** fresh aligned finite in-range value can qualify; stale frame, geometry mismatch, absent value, short/misaligned list, NaN/infinity, and out-of-range values cannot qualify as metric. These cases must not fabricate a metric label; heuristic fallback remains distinguishable and approximate.
4. **Center path and hysteresis:** eligible center-path entry and side-position exclusions; no distance crossing inferred from heuristic values; approach/near/risk escalation interactions; threshold oscillation does not repeatedly alert; re-arm and state expiry follow approved hysteresis semantics; existing `minEscalationGap` remains effective.
5. **Lifecycle/scheduler:** repeated `decide` does not mutate state; only confirmed start commits; existing cooldown/dedup/preemption behavior stays intact; parked pending decision revalidates against current metric eligibility and active detector identity; stale/model-switched pending alert is rejected; non-accepted/cancelled requests do not arm hysteresis.
6. **Quick Scan isolation:** direct Quick Scan remains user-initiated, summarizes the full scene by existing behavior, and does not read/write automatic alert history or custom distance hysteresis.
7. Run the targeted test files and full `flutter test` and `flutter analyze`. Physical Android validation is required before promoting proposed thresholds/defaults: test fresh/stale depth, geometry changes, transitions across each threshold, center/side relevance, repeated threshold oscillation, model switch with pending speech, audible dedup/cooldown, and Quick Scan independence. Record device/runtime limitations; passing unit tests does not establish metric calibration or audible latency.

## Initial tuning defaults and device validation

**No new custom-specific threshold or hysteresis default is verified by the analysis or source inspected.** Existing verified values are the depth freshness max age of 1000 ms, metric valid range 0.1–80 m, and descriptive bands at 1.5 m and 4.0 m. Those are current data/fallback contracts, not automatically approved custom-alert trigger/hysteresis settings.

Implementation may expose constants/configuration for custom trigger and reset thresholds, but their initial values, sample debounce, and behavior on invalid/stale metric data remain **Needs Verification** and must not be silently chosen. Proposed policy for review: use the existing metric near/medium boundaries as candidate trigger levels, require center-path relevance for the new distance-based custom alert, preserve existing priority tiers and existing `minEscalationGap`, and use a separate lower reset boundary to re-arm. This is a proposal only, not an approved default. Device validation must assess alert stability and false/repeated warnings, not calibrate the depth model or imply ground-truth distance.

- **[product-decision]** Confirm combination precedence: may fresh metric distance promote a low-priority custom class, and may metric risk outrank a higher object-priority candidate? Proposed implementation keeps shared candidate ordering and lets metric evidence affect only that candidate's alert risk/eligibility.
- **[product-decision]** Confirm metric trigger thresholds and distinct hysteresis reset thresholds, sample debounce/consecutive-frame rule, re-arm timing, and behavior when metric evidence becomes unavailable. Existing 1.5 m / 4.0 m bands are observed but are not verified as alert thresholds.
- **[product-decision]** Confirm center-path semantics: should center be a required qualifier only for distance-triggered custom alerts, or should side-position distance alerts be eligible too? Proposed behavior requires center for the new distance trigger and does not treat center alone as metric evidence.
