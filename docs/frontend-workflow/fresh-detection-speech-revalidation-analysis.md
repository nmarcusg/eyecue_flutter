## Active detector path and shared callback flow

- The current screen set contains [`UltralyticsDetectionScreen`](../../lib/screens/ultralytics_detection_screen.dart), wrapped by [`EngineDetectionScreen`](../../lib/screens/engine_detection_screen.dart); there is no [`detection_screen.dart`](../../lib/screens/detection_screen.dart) or active separate Custom EyeCue screen in `lib/screens/`. Current task scope therefore has one active detector-result callback path, not two parallel detector callbacks. Engine-specific naming/docs must not imply a removed second path.
- [`_handleStreamingData`](../../lib/screens/ultralytics_detection_screen.dart) rejects callbacks if detection is inactive/paused or if their callback epoch does not match both the current native view epoch and active epoch. It timestamps the first observable receipt with `DateTime.now()`, parses the native result, marks model readiness on the first payload, converts results, gets currently fresh depth estimates, then calls [`AssistiveDetectionController.updateDetections`](../../lib/services/assistive_detection_controller.dart).
- The native result callback has no frame timestamp or session envelope; screen code explicitly calls pre-result timestamps unavailable. Its local epoch rejects callbacks from known prior native views, but does not establish whether a delayed result produced before pause/resume was delivered after resume within the same native epoch. Existing screen comments document a similar strict freshness limitation for overlay presentation; speech currently receives no stronger provenance than that callback.
- [`updateDetections`](../../lib/services/assistive_detection_controller.dart) analyzes detections, updates tracking with the optional `timestamp` argument, records each detection, and submits the analyzed set/tracks for speech. The screen passes `resultReceivedAt` and meters but no explicit tracker timestamp; [`ObjectTracker.update`](../../lib/services/object_tracker.dart) therefore uses its `DateTime.now` clock. Result receipt and tracker event time are separate wall-clock reads.

## Tracker visibility, retention, and timestamp behavior

- The tracker matches class-aware geometry, tracks smoothed box/center/area and hit/miss evidence, and returns only tracks observed in the current update. Missing tracks remain internally for at most four missed updates by default; those retained tracks are not included in the returned speech track list and cannot directly make a disappeared object eligible for speech. The default cap is 64 tracks.
- Track IDs reset to 1 on `reset()`. The detector-model change handler clears correction state, resets the assistive controller/tracker and cancels a queued detection request before stamping the new model identity. The reset clears associations but does not itself establish a cross-service session generation for TTS callbacks already underway.
- Tracker timestamps are `DateTime` wall-clock values. Track age is `timestamp.difference(firstSeen)` and `lastSeen` is assigned from each update; no monotonicity guard rejects equal or regressing timestamps. `ObjectTracker` accepts caller-supplied timestamps unchanged. The active screen does not pass one, so its default wall clock governs. TTS and alert policy also use `DateTime` (their injected clock defaults to `DateTime.now`); pending-request validity and cooldown comparisons use wall-clock differences, not monotonic elapsed-time sources.
- The available direct candidate for timestamp changes is the tracker/service contract and its tests; adding a monotonic source or event timestamp is not an established convention. The intent and acceptable behavior under device clock adjustment are **Needs Verification [product-decision]**.

## Alert policy and pending speech behavior

- [`AlertPolicy.decide`](../../lib/services/alert_policy.dart) evaluates the current detection list and current observed tracks; it keeps bounded suppression/escalation history. Its default parked-decision validity is 1500 ms, and state TTL is 30 seconds. A decision records creation time, suppression identity, optional target/track and detector identity, but does not store a source-result timestamp or a source-generation/session token.
- Accepted alert history is committed only after a confirmed platform `onStart` callback. The TTS service's [`_handleStart`](../../lib/services/tts_service.dart) records the actual start time and invokes `policy.commitStarted`; completion/cancel/reconciliation does not create suppression history. Parked policy decisions are checked with `shouldSpeakPending` immediately before start, and rejected if they are no longer current or detector identity changed.
- This revalidation means the scheduler avoids some superseded duplicate speech, but it is not a fresh-detection check: the policy receives no latest-result timestamp/state and the parked decision's target can remain the old detection. A recent result may not include that object while suppression history/track state remains live, and a queued decision can still pass eligibility based on alert history unless the specific state has changed. Whether absence in a newer result must invalidate an active or queued announcement is the central behavior requirement to specify.
- TTS is explicitly bounded to one active and one pending request; same/higher-priority arrivals replace the pending item under scheduler rules. Automatic detection requests have policy validity (default 1500 ms). `startConfirmationTimeout` is 1000 ms, `reconciliationTimeout` 400 ms, and completion/watchdog plus recovery/quarantine logic govern callbacks with no utterance IDs. The policy and scheduler already have extensive tests for start/cancel order, stale queued decisions, recovery and late callbacks.
- Platform callback ordering and actual cancellation latency remain runtime limitations; no callback carries an utterance ID, so the service serializes and quarantines callbacks rather than matching IDs. A new freshness boundary must preserve this reconciliation model and must not treat a stop request as proof that audio has ended.

## Depth freshness is independent from detection freshness

- The screen considers a depth frame usable only when its timestamp is within configured `depthStaleAfterMs` (1000 ms) and its rotation/geometry matches current detection geometry. `_metersFor` passes per-detection estimates only in that case; absent/stale/mismatched depth returns null, then distance/proximity falls back to box-size heuristic in spatial analysis.
- Depth timestamps come from the depth model event/frame path and are tested for age. They are not detector-result timestamps and cannot prove that an object observation is fresh. The screen currently computes depth freshness at detector callback time and takes the latest depth frame; this only describes depth data, not result production time.
- Existing depth smoother state is keyed by tracker ID and is reset on model changes along with tracker state. Any speech freshness rule must avoid conflating stale depth, missing metric samples, or approximate box proximity with stale detector observations.

## Pause, stop, background, Quick Scan, and repeat boundaries

- Result callbacks are dropped while local detection is inactive or paused. Pause stops depth cadence; resume restarts it. Stop advances the native callback epoch, stops native detection/depth, clears current detections/tracks/overlay state, and reports stopped. Model switch stops detection, resets assistive state and cancels queued automatic detection speech.
- No app lifecycle observer was located in the active screen for background/foreground invalidation. Background behavior and whether an in-flight native callback or TTS request should be invalidated on lifecycle transitions are not demonstrated by the inspected code; treat as unverified rather than assuming OS suspension cancels audio.
- Quick Scan is an explicit user-initiated scene summary with its own 1500 ms request validity; it does not create alert policy/suppression state. The screen enables it only in Ready/healthy-fallback status and gesture dispatch gates it to those states. [`repeatLast`](../../lib/services/tts_service.dart) replays the last utterance that actually started, with a 10-second request validity; swipe-down dispatches repeat independently of the detector-result callback. Existing semantics intentionally distinguish this user replay from automatic detection alerting.
- Requirement ambiguity: should a deliberate Quick Scan or repeat remain speakable when the last detector result is no longer fresh, or should only automatic object speech be revalidated? This is not inferable from current behavior.

## Open Questions / Needs Verification

- **[product-decision]** Define fresh detector observation: require the target object to appear in the latest accepted detector result, require a minimum number of recent hits, or only require that the selected decision itself is recent? Specify the time window/number of observations and absence policy.
- **[product-decision]** Define treatment of speech already confirmed started when a newer result no longer contains the target. Proposed conservative bounded grace: allow already-started detection speech to finish only until the existing TTS completion watchdog budget for that utterance (existing completion-budget logic); do not use a new multi-second grace. This is grounded in the scheduler's current completion/recovery bounds but still needs product approval. Alternatively request immediate stop, noting actual audible cancellation is not guaranteed.
- **[product-decision]** Define queued/pending speech behavior on an empty, low-confidence, or non-matching newer result: cancel immediately, retain only through the existing alert decision validity (1500 ms), or another explicit policy. Keeping the existing 1500 ms expiry alone is not proof of fresh target presence.
- **[product-decision]** Confirm Quick Scan and Repeat Last remain deliberate user actions exempt from automatic detection freshness, including whether Quick Scan may speak a snapshot that became stale while parked behind active speech.
- **[product-decision]** Specify whether pause/stop/model-switch/background invalidates active automatic speech, pending speech, or both; current model switch explicitly cancels pending detection speech but pause/stop do not show an equivalent scheduler invalidation in inspected code.
- **[Needs Verification — source limitation]** Ultralytics result payload exposes no result production timestamp/correlation token in the screen callback. Receipt time cannot establish how old the underlying frame is; strict source-time freshness may require an approved native/plugin result-envelope change.
- **[Needs Verification — inferred-from-codebase]** Decide whether freshness state belongs in `AssistiveDetectionController`, `AlertPolicy`, or `TtsService`. Policy owns target selection/eligibility; controller receives result sets; TTS owns pending/active request lifecycle. Avoid duplicated independent freshness clocks.
- **[Needs Verification — clock semantics]** Decide if wall-clock `DateTime` is acceptable for event ordering/age. Current tracker and scheduler use wall time, permit equal timestamps, and do not enforce monotonicity; a monotonic elapsed clock would need to be introduced at the chosen boundary and cannot reconstruct native production time.
- **[Needs Verification — worktree]** Recheck current git status before implementation. The prior analysis snapshot lists six modified files, including the directly adjacent spatial test, but is not guaranteed current.
- **[Needs Verification — runtime]** Physical Android validation of alert cancellation timing, actual TTS start/completion callback order, background transitions, and device-clock changes was not performed in this analysis.
