## 1. Executive Summary

The current EyeCue Flutter codebase is a **technically strong, developer-facing computer-vision prototype** — and **not yet the assistive application described in the thesis**.

The thesis is titled *"EyeCue: Machine Learning-Based Real-Time Object Recognition and **Audio Guidance System** for the Visually Impaired."* Its central product promise is a **blind-first mobile app** that:

1. detects objects in real time on-device (YOLOv8 / TFLite),
2. **speaks detected objects plus their relative position** via TTS,
3. classifies objects by **priority/obstacle importance** and raises an audio alarm for dangerous barriers,
4. is operated **non-visually via gestures** (start/exit, quick scan, repeat last alert, pause/resume),
5. exposes a small set of **screens** (Home, Detect, Settings, Help, Logs & Reports), and
6. **records telemetry** for research evaluation (detection logs, confidence, inference time, FPS, charts).

**What the code actually does:** captures the camera, runs YOLOv8 in a persistent isolate, draws bounding boxes with confidence on a preview, and shows a developer **Metrics/Detections** panel with FPS/latency/confidence and file-based forensic logs. **There is zero audio output, zero spatial interpretation, zero priority logic, zero gesture interaction, zero settings, and zero charts.** The single screen is a silent, metrics-oriented camera viewer.

**Bottom line:** The ML engine (domain A) is roughly **80% complete**, but the assistive layers that constitute the thesis's reason for existence — audio guidance, spatial position, priority, accessibility/interaction (domains B, C, D) — are **0% implemented**.

> **Weighted overall thesis-product completion: approximately 30% (range 25–35%).**
> This deliberately does **not** match the project's self-reported **~60%**, which counts only the ML/debug pipeline and excludes the entire audio-assistive product layer. See [§11](#11-completion-estimates).

The **single largest mismatch** with the thesis is the complete absence of the **audio guidance system** (TTS + relative-position speech + priority alarms). Every other critical gap (spatial interpretation, gestures, screens, research dashboard) depends on or follows from that.

## 2. Thesis-Defined Product Scope

Extracted directly from the thesis PDF. This is the functional contract the final product must satisfy.

### 2.1 Core system (Ch. 1–2)

| Thesis requirement | Detail from thesis |
|---|---|
| Real-time object detection | YOLOv8, "high-speed object detector and recognizer" |
| On-device ML | TensorFlow Lite, "model runs entirely on the device without relying on internet connectivity" |
| Smartphone camera | Primary input ("smartphone camera is the first input that continuously records visual information") |
| Audio feedback / TTS | "verbal output generated by the EyeCue application through text-to-speech technology, **which informs the user about detected objects and their relative position**" |
| Object identity | Recognized class (persons, chairs, doors, vehicles…) |
| Confidence | "assign objects the confidence scores"; thresholded in a "decision stage" |
| Relative position | "barrier and its **approximate position relative to the user**" (Detection screen) |
| Approximate distance / spatial info | Short-range detection; approximate position; no GPS/pathfinding (Limitations) |
| Movement / navigation relevance | Literature motivation (object type **and movement**); detection of navigation-space objects |
| Priority / obstacle importance | "objects identified are classified based on the **priority levels**, with obstacles of high priority identified… On recognizing a potentially dangerous barrier, the system will generate an **audio alarm**" |

### 2.2 User interaction (Ch. 2 Conceptual Framework + Ch. 3 Detection screen)

- User "interacts with the application through **gestures and options**, the **change of the detection sensitivity**, and the provision of control gestures, including **repeating an output** or **signaling errors**."
- "In case of incorrect detections or missing objects the user may give **corrective input by gesture** or using an **in-application correction interface**."
- Detection-screen gestures (explicit list — do not invent more):
  - **Two-finger double tap** — start or exit detection mode
  - **Three-finger tap** — perform a quick environmental scan
  - **Swipe down** — repeat the most recent audio alert
  - **Single tap** — pause or resume detection

### 2.3 Application screens (Ch. 3 High-Fidelity Prototype)

| Screen | Thesis description |
|---|---|

| **Detection** | Core screen. Camera → YOLOv8 → bounding boxes + confidence; objects classified by **priority**; **audio alarm with type + approximate position** for dangerous barriers; **gesture controls**. |
| **Settings** | **Vibration feedback**, **Automatic detection startup**, **Low power mode** (battery optimization), and a **"Logs and Report"** option. "Adjusted to user preferences and device capability." |
| **Help** | "Guide the user on how to operate the application… descriptions of system operations, **gestures and usage suggestions**." |
| **Logs & Reports** | Researcher/developer-facing **data visualization**. Charts tab: **Detection Frequency**, **Inference Latency**, **FPS**, and a **comparative chart (Accuracy, Precision, Recall, F1-Score)**. Kept inside Settings "to prevent overcomplicating the interface for the visually impaired user." |

### 2.4 Settings / configuration (thesis-defined)

- Vibration feedback
- Automatic detection startup (auto-start)
- Low-power mode for battery optimization
- Logs and Report option
- Detection sensitivity (user-changeable, per Conceptual Framework)

### 2.5 Research / telemetry (thesis-defined)

- The app "records detection results, confidence scores, inference time, and other performance metrics."
- During testing the app records: **detected objects, prediction confidence scores, bounding box coordinates, inference time and FPS, time-stamped system logs**, plus **errors and device statistics**.
- Data visualization: **Detection Frequency chart** (per day), **Inference Latency graph**, **FPS graph**, comparative **Accuracy/Precision/Recall/F1** chart, plus overview metrics + detailed logs on structured tabs.

### 2.6 Research evaluation (Ch. 3)

| Metric | Thesis requirement |
|---|---|
| Accuracy / Precision / Recall / F1 | Computed from detection logs / confusion matrix |
| mAP | Target **≥ 0.85** (0.933 @ IoU 0.5 cited as strong) |
| FPS | **≥ 15 FPS** targeted; 30 optimal, **10 adequate** |
| Latency | **≤ 300 ms**; ~303 ms considered "highly efficient" |
| SUS | 10-item System Usability Scale, benchmark **68** |
| Statistical testing | **One-sample t-test** of mean SUS vs 68; reject H₀ if p < 0.05 |
| Participants | ≥ **30** visually impaired participants, purposive sampling (WHO definition), controlled navigation testing, chest-mounted phone, supervised |
| Hypothesis | H₀: mAP < 0.85 **or** speed < 15 FPS **or** latency > 300 ms; H₁: mAP ≥ 0.85 **and** ≥ 15 FPS **and** ≤ 300 ms |

**In-app vs external distinction:** most evaluation metrics (mAP, precision/recall/F1 computation, SUS scoring, t-tests, participant recruitment) are **research procedures/tooling**, not shipped-app features. What the *app* must do is: (a) be usable by a blind person, and (b) **record** the raw telemetry (detections, confidence, inference time, FPS, timestamps) so those analyses can be performed.

## 3. Current Flutter Architecture

Verified directly from the code (not from docs).

### 3.1 Entry point

[`lib/main.dart`](../lib/main.dart) → `MaterialApp(home: CameraScreen())`. **Single screen, no routing, no navigation.**

### 3.2 The only screen — [`lib/screens/camera_screen.dart`](../lib/screens/camera_screen.dart)

- Camera init (`ResolutionPreset.low`, YUV420, `permission_handler`), starts image stream.
- Frame-dropping busy gate (`_isInferring`).
- Per-frame orientation math via [`BoxTransform`](../lib/models/box_transform.dart).
- Sends Y/U/V planes + geometry + orientation to the isolate.
- Renders: strict 3:4 portrait preview (`FittedBox` contain) + [`BoundingBoxPainter`](../lib/widgets/bounding_box_painter.dart) overlay + permanent bottom [`InfoPanel`](../lib/widgets/info_panel.dart) with **Metrics** and **Detections** tabs.
- Maintains a 50-entry in-memory detection history (label, confidence, timestamp).
- **No TTS, no haptics, no gestures, no pause/resume, no settings, no navigation, no permission-denied UI** (denied permission → silent infinite spinner).

### 3.3 Inference service — [`lib/services/inference_isolate.dart`](../lib/services/inference_isolate.dart)

- Persistent isolate (`Isolate.spawn` once), single `Interpreter`, pre-allocated dtype-matched buffers.
- Runtime model introspection ([`ModelMetadata`](../lib/models/model_metadata.dart), [`tflite_flatbuffer.dart`](../lib/models/tflite_flatbuffer.dart)).
- Manual YUV420→RGB (stride-aware), nearest-neighbor resize, metadata-driven quantization.
- Input-tensor rotation/mirror to upright (orientation fix).
- Argmax per anchor → confidence threshold 0.25 → **class-wise NMS (IoU 0.45)**.
- Emits `List<Detection>` via a broadcast `StreamController`. **This stream is the natural integration point for every missing assistive feature.**
- Error propagation via `{'type': 'error'}`; **no isolate restart recovery**.

### 3.4 Models

- [`Detection`](../lib/models/detection.dart): `classId`, `label`, `confidence`, normalized `Rect box`. **No spatial/priority fields.**
- [`BoxTransform`](../lib/models/box_transform.dart): orientation math.
- [`ModelMetadata`](../lib/models/model_metadata.dart), [`tflite_flatbuffer.dart`](../lib/models/tflite_flatbuffer.dart), [`png_encoder.dart`](../lib/models/png_encoder.dart): introspection/diagnostic support.

### 3.5 Widgets

- [`bounding_box_painter.dart`](../lib/widgets/bounding_box_painter.dart): box + label + confidence overlay (complete).
- [`info_panel.dart`](../lib/widgets/info_panel.dart): Metrics + Detections tabs (developer-oriented).
- [`debug_overlay.dart`](../lib/widgets/debug_overlay.dart): **retained but unused** (confirmed: not imported by the screen).

### 3.6 Services / diagnostics

- [`forensic_log.dart`](../lib/services/forensic_log.dart): file-based structured logs + PNG dumps under `<documents>/debug/run_*` (uses `path_provider`). Developer/research diagnostic, not a user-facing "Logs & Reports" module.
- [`inference_probe.dart`](../lib/services/inference_probe.dart) / [`input_probe.dart`](../lib/services/input_probe.dart): disabled diagnostic probes.

### 3.7 Dependencies ([`pubspec.yaml`](../pubspec.yaml))

Used: `camera`, `tflite_flutter`, `permission_handler`, `path_provider` (via forensic log). **Declared but unused:** `flutter_tts`, `flutter_riverpod`, `fl_chart`. No `shared_preferences` (so no settings persistence), no vibration/haptics package.

### 3.8 Tests

[`test/widget_test.dart`](../test/widget_test.dart) is the **Flutter counter boilerplate** — it references `Icons.add` / `find.text('0')` that do not exist in the app and would fail. **Zero functional tests.**

### 3.9 Android config

[`android/app/build.gradle.kts`](../android/app/build.gradle.kts): package `com.example.eyecue_flutter`, `minSdk = flutter.minSdkVersion` (default 21), release build signs with the **debug** keystore. Thesis targets Android 10 (API 29)+ and implies a `com.eyecue` package.

## 6. Assistive Functionality Gap Analysis (domains B, C, D)

## 7. Spatial Guidance Gap Analysis

> **Explicit finding: spatial position is NOT implemented.**

The thesis's operational definition of *Audio Feedback* is explicit: TTS "informs the user about detected objects **and their relative position**," and the Detection screen requires announcing "the type of the barrier and its **approximate position relative to the user**."

What the code actually computes is only the **raw detection geometry**:

- [`Detection.box`](../lib/models/detection.dart:7) is a normalized `Rect` (e.g. `left 0.62, top 0.31, width 0.15, height 0.41`).
- These coordinates are used **only** to draw boxes on the preview ([`bounding_box_painter.dart`](../lib/widgets/bounding_box_painter.dart)).

**The presence of `box.center.dx` does not equal "left/right" being implemented.** There is:

- ❌ no left/right/center classification (box-center-X vs frame thirds/center band),
- ❌ no relative-position phrasing ("on your left", "straight ahead"),
- ❌ no approximate-distance estimation (box height/area as a proxy for proximity — not implemented),
- ❌ no movement/approach detection (no cross-frame tracking),
- ❌ no obstacle-priority tiering,
- ❌ no context-aware announcement.

The raw geometry is the correct **seed data** — a spatial-interpretation module can be added as a pure function over `Detection.box` without touching the ML pipeline — but the user-facing spatial guidance the thesis requires does not exist today.

## 8. Research / Evaluation Gap Analysis

**What exists:** strong raw instrumentation — per-frame inference latency, camera/inference FPS, confidence stats, forensic file logging, PNG dumps, per-run session dirs. This is arguably ahead of a typical undergraduate project ([`forensic_log.dart`](../lib/services/forensic_log.dart), [`info_panel.dart`](../lib/widgets/info_panel.dart)).

**What is missing to satisfy the thesis:**

1. **Charts / data visualization** — the thesis specifies Detection-Frequency, Inference-Latency, FPS, and Accuracy/Precision/Recall/F1 charts. `fl_chart` is declared but unused. ❌
2. **Structured, exportable logs** — forensic logs are developer-oriented text files; the thesis "Logs and Reports" module implies per-session records a researcher can open, with overview metrics + detailed logs on tabs. 🟡
3. **Accuracy/precision/recall/F1 computation** — not performed anywhere. ❌ (This belongs in research tooling; the app only needs to record the raw detections.)
4. **mAP** — not computed; model is pre-trained COCO; no custom-dataset evaluation artifacts in the repo. ❌ (External tooling.)
5. **Formal FPS/latency results** — metrics are *measured* but there is no results report; end-to-end **audio** latency cannot be measured because there is no audio. 🟡
6. **SUS / participant study / t-test** — research procedures; not started. ⚪ External. The blocker is that the app is not yet usable by a blind participant.

**In-app vs external:** The app must record (detections, confidence, inference time, FPS, timestamps, errors) and render researcher charts. It should **not** compute mAP/SUS/t-tests inside the app — those are offline analysis steps.

## 12. Critical Missing Features

### The single biggest mismatch

> **The audio guidance system is completely absent.** The thesis product is fundamentally an *audio* guidance system ("informs the user about detected objects and their relative position," "audio alarm" for dangerous barriers, gestures that repeat audio alerts). Today the app produces **zero sound**. `flutter_tts` being in [`pubspec.yaml`](../pubspec.yaml:20) is not TTS; there is no TTS code anywhere. Everything else critical depends on or follows this gap.

### The next 5 highest-impact gaps (prioritized)

1. **Spatial interpretation + priority** (thesis: relative position, obstacle priority, audio alarm). The raw boxes exist; the semantics do not. This is the content of the audio feedback.
2. **Gesture-based nonvisual interaction** (thesis: 2-finger double-tap start/exit, 3-finger scan, swipe-down repeat, single-tap pause/resume). Without it the app is not operable by its target user.
3. **Application screens & navigation** (Home / Detect / Settings / Help, bottom nav). The app currently boots into a developer camera screen.
4. **Settings with persistence** (vibration, auto-start, low-power, sensitivity). Required Settings screen; no `shared_preferences`.
5. **Permission-denied UI + isolate restart recovery + release config** (Play Store/defense importance: a blind user cannot be left on an infinite spinner; a crash must self-heal; release must not sign with the debug keystore).

## 14. Risks / Dependencies

1. **Thesis metric inconsistency (defense risk):** Hypothesis states ≥15 FPS **and** ≤300 ms latency, but 300 ms implies ≤3.3 FPS. [`docs/research-notes.md`](../docs/research-notes.md:30) already flags this. Must be redefined (camera FPS vs detection FPS vs end-to-end audio latency) before defense.
2. **Thesis names React Native** in the "Software Framework" section while the implementation is Flutter. The methodology is stated as technology-agnostic, so this is a **documentation inconsistency in the thesis that should be revised** — not a reason to return to React Native.
3. **Thesis "auto-start" / Home status card** implies auto-start + a Home screen; neither exists — the thesis and implementation must be reconciled.
4. **XNNPACK SIGSEGV** blocks throughput; CPU-only may fail the ≥15 FPS hypothesis on the target device. Mitigate with NNAPI/GPU/fallback + realistic metric definitions.
5. **Participant recruitment** (≥30 VI participants, ethical consent, supervised sessions) is a schedule risk and requires a *usable* audio app first.
6. **Dependency on `flutter_tts`/`shared_preferences`/vibration** to be added — minor, but platform quirks (TTS engine availability) need testing.
7. **Battery drain** (thesis lists it as a limitation) — Low-power mode and camera-deactivation-on-pause are required mitigations.

## 15. Explicit "What Is Already Complete"

Verified in code:

- **Camera acquisition:** init, permission request, YUV420 low-resolution stream, frame-dropping busy gate, resource cleanup.
- **Inference engine:** persistent isolate, single `Interpreter`, runtime model introspection, dtype-matched buffers, raw `ByteBuffer` I/O, dynamic NHWC/NCHW handling, FLOAT16/INT8/UINT8 support.
- **Preprocessing:** stride/pixel-aware manual YUV420→RGB (I420 + NV12/NV21), nearest-neighbor resize, metadata-driven quantization.
- **Orientation:** device-independent `BoxTransform`; input rotated/mirrored to upright; on-device portrait detections validated (0 → 0.91).
- **Post-processing:** argmax per anchor, confidence threshold 0.25, class-wise NMS (IoU 0.45).
- **Detection output:** class label, confidence, normalized bounding box; streamed to UI.
- **Overlay:** bounding boxes + label pills + confidence via `CustomPainter`, aligned with the preview (`applyBoxFit`).
- **Developer instrumentation:** metrics panel (FPS, latency, confidence, resolutions, model info), 5-second performance summaries, forensic file logging with PNG dumps and auto-diagnosis, error propagation to the main isolate.
- **On-device, offline, privacy-preserving** end-to-end detection.

This is genuinely strong, careful ML engineering — it should be neither understated nor allowed to mask the missing product layer.

## 17. Conclusion

> **If we froze development today, what genuinely works:** a real-time, on-device YOLOv8/TFLite detection pipeline — camera → isolate → preprocessing → inference → NMS → bounding boxes → developer metrics and forensic logs — running offline on Android. This is roughly **80% of the computer-vision engine** and perhaps **10% of a usable product**.

> **What is still missing:** everything that makes EyeCue the *assistive audio-guidance system* the thesis describes — text-to-speech, relative-position and priority-aware spoken feedback, gesture-based nonvisual interaction, the Home/Settings/Help/Reports screens, and the research dashboard.

> **What must be completed before we can honestly call this the final EyeCue product:** (1) the audio guidance core (TTS + spatial position + priority), (2) the gesture interaction model, (3) the full screen/navigation/settings architecture, (4) telemetry export and charts for evaluation, (5) the controlled usability/accuracy study with visually impaired participants, and (6) production hardening (permissions, recovery, release, Play Store).

In short: **the eyes of EyeCue are nearly complete; the voice and the hands — its entire reason to exist — do not exist yet.** The honest thesis-product completion today is **approximately 30%**.
